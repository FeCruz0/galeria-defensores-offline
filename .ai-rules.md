# AI-Rules: Galeria de Defensores (Android/Kotlin Edition)

## 0. Protocolo de Operação Silenciosa (Token Saving)
- **Sem conversa:** Proibido saudações, confirmações ("Entendido", "Vou fazer") ou explicações redundantes. Inicie a resposta diretamente com o código ou documento solicitado.
- **Diferenciais (Partial Updates):** Jamais reescreva um arquivo inteiro. Use `// ... código existente` para omitir partes não alteradas. Forneça apenas o diff ou a função específica.
- **Strict JSON:** Para trocas de dados entre agentes, use apenas JSON puro sem blocos de texto explicativo.
- **Leitura seletiva:** Antes de ler um arquivo, consulte o `context.md` para saber se a informação já está documentada. Evite reler arquivos grandes quando o trecho relevante já foi extraído na sessão.
- **Regra de Símbolos:** Para entender uma dependência desconhecida, peça a assinatura do método/interface (`fun`, `interface`, `abstract class`), nunca a implementação completa. Exemplo: prefira `CharacterRepository.kt` (interface/header) a `CharacterRepositoryImpl.kt` (corpo).
- **Git: Proibido Comitar:** É expressamente proibido que a IA execute `git commit`. A IA deve apenas preparar a mensagem e o comando, deixando a execução para o usuário.

## 1. Metodologia BMAD (Arquitetura Android)
Siga o ciclo de vida BMAD para qualquer mudança estrutural:
1. **Análise:** Identificar se a mudança afeta o Modelo (`Character.kt`), o Banco (Room/DAO) ou a UI (Fragment/ViewModel).
2. **Planejamento:** Criar/Atualizar artefatos em `artifacts/`. O "Implementation Plan" deve listar os impactos em Injeção de Dependência (Hilt) e Serialização.
3. **Solução (Prompt Compression):** Usar **pseudocódigo** ou descrição de fluxo em português nas discussões de Brainstorm/Solução. Só transformar em Kotlin final na fase de **Implementação**. Exemplo válido em Brainstorm: `se nome mudou → validar unicidade → salvar; senão → salvar direto`.
4. **Implementação:** Escrita estrita do código Kotlin planejado.

**Documentação Primeiro:** Nenhuma linha de código deve ser alterada ou criada antes da aprovação de um "Implementation Plan" documentado pelo usuário.

## 2. Framework Superpowers (Engenharia & TDD)
1. **Plan:** Quebrar em tarefas atômicas no `task.md`.
2. **TDD (Obrigatório — Incremental):**
   - Criar o teste unitário em `src/test` (JUnit/MockK) e **parar**.
   - Aguardar confirmação explícita do usuário ("OK", "pode continuar") antes de escrever qualquer código de implementação.
   - O teste deve **falhar (Red)** antes da implementação.
   - Implementar o código mínimo para o **Green** somente após o OK.
3. **Review:** Verificar se a implementação não quebrou o `calculateScore()` ou o `kotlinx.serialization`.

*Ignorar o TDD e pular para a implementação final é expressamente proibido.*

## 3. Diretrizes Técnicas Específicas (Kotlin/Android)
- **Imutabilidade:** Priorize `val` e `data class`. Use `copy()` para alterações de estado no ViewModel.
- **Hilt:** Use `@Inject` no construtor. Evite `EntryPointAccessors` salvo necessidade estrita.
- **Room & Serialization:**
  - Toda nova propriedade em `Character` deve ser anotada com `@Serializable`.
  - Converters devem usar `Json.decodeFromString` / `Json.encodeToString`.
  - Alterações estruturais em modelos exigem migração no `AppDatabase`.
- **UI Reativa:** Use `collectAsStateWithLifecycle` (ou `repeatOnLifecycle`) para evitar vazamento de memória.
- **Adaptadores:** Nunca inicialize um `RecyclerView.Adapter` mais de uma vez para o mesmo RecyclerView. Use `updateData()` para atualizar o estado.
- **StateFlow:** Em `uiState` collectors, sempre use `ruleSystemViewModel.ruleSystem.value` (estado ao vivo) em vez de snapshots do `uiState` para operações de sistema de regras.
- **Build:** Usar `docker-compose run --rm android-build ./gradlew <task>` para compilar e testar. Nunca usar Gradle local diretamente.

## 4. Regras de Negócio Inegociáveis (Knowledge Items)
1. **Cálculo de Pontos:** O parsing de custos DEVE usar a Regex `-?\d+`. Nunca converter strings de custo manualmente.
2. **IDs Únicos:** Ao mover itens do Catálogo para a Ficha, gerar novo `UUID` via `CharacterViewModel` é obrigatório. Repetir IDs de catálogo na ficha é erro crítico.
3. **Itens Modulares:** Se `isModular == true`, o custo base é ignorado; usar `computedCostPt()` (soma dos modificadores).
4. **Exclusão de Recursos:** Sempre exibir `AlertDialog` de confirmação antes de invocar `removeResourceDefinition()`.
5. **Salvamento de Sistema:** `RuleSystemRepository.saveSystem` valida unicidade de nome **somente se o nome for alterado**. Não lançar exceção para edições de recursos/atributos sem mudança de nome.
6. **Persistência:** `saveRuleSystem()` no ViewModel deve ter `try-catch` com reversão para `previousSystem` em caso de falha.
